Contact normalizer recipe function

Spec approval

A reusable recipe function that any CRM or marketing flow can call to clean one contact record. It takes first name, last name, email and phone (all optional), trims and standardises them (title-cased names, lower-case email, phone as digits with an optional leading "+"), builds a full name, and reports whether the record is usable (is_valid) plus a list of problems (issues). It never fails on bad input: it always returns a result, with is_valid=false and issues instead.

How we'll know it works

  • All acceptance tests pass, including bad and empty input, with zero failed jobs
  • Responds in under 2 seconds per call
  • Issues text is understandable by a non-technical user without documentation
  • At least one other recipe reuses it within the first month (adoption)

The function never breaks the caller: bad input gives is_valid=false and plain-language issues ("invalid email", "missing email", "invalid phone"). Output field names match the input names so builders can map them without guessing.

If something goes wrong
Bad or missing input is not a failure: the function returns normally with is_valid=false and the problems listed in issues. Any unexpected error inside the function is caught, written to the job log with Logger (error type/message only, no raw names, emails or phones), and the function still returns is_valid=false with issues containing "internal error", so the caller never sees a failed call.

The step-by-step recipe flow is drawn at the design approval.

Rules it follows

output.first_name
trim; title-case each word (e.g. " aNNA " -> "Anna"); missing/blank -> ""
output.last_name
trim; title-case each word (e.g. " SMITH " -> "Smith"); missing/blank -> ""
output.full_name
join the non-empty parts with a single space; "" when both are empty
output.email
trim; lower-case; missing/blank -> "" (adds issue "missing email")
output.is_valid / output.issues
email "looks valid" = exactly one "@", non-empty part before it, a domain after it that contains at least one "." with non-empty labels, and no whitespace; otherwise adds issue "invalid email". The exact pattern is the Architect's call within this rule.
output.phone
trim; keep only digits 0-9, plus a "+" only if it is the first non-space character; missing/blank or no digits -> "" (e.g. " +1 (415) 555-0100 " -> "+14155550100")
output.is_valid
true only when issues is empty; false otherwise

Decisions needed from you

Q1 · Should a missing first or last name make the contact invalid? No. Only the email decides is_valid; names are optional and never add issues.
Q2 · How should issues be written? Short lowercase phrases joined with "; " in a fixed order (email first, then phone), e.g. "invalid email; invalid phone". "" when there are none.
Q3 · How should names with apostrophes, hyphens or particles be capitalised? Capitalise the first letter after a space, hyphen or apostrophe ("o'neil-SMITH" -> "O'Neil-Smith"); no special Mc/van rules.
Q4 · What counts as a phone problem, and what about extensions? A missing phone is fine (no issue). A phone with fewer than 7 digits adds "invalid phone" and makes is_valid false. Anything after "ext" or "x" is dropped ("415.555.0102 ext 7" -> "4155550102").
Q5 · Should a missing field come back as "" or null? "" (empty text), so callers never have to handle nulls.
Q6 · Should an invalid email be returned or blanked? Returned, trimmed and lower-cased, so callers can show it back to the user.
Q7 · Peak volume of 200 calls/hour and fit within Free-plan credits? Accept for now; the Operate stage measures real usage and alerts if credits run low.
Q8 · Workato keeps each job's inputs and outputs in job history, which would include personal data. Acceptable? Acceptable in dev with synthetic test data only. Before real customer data, decide on data masking or shorter job retention (plan-dependent).

Not included

  • Writing or updating contacts in any CRM or marketing app (callers do that)
  • Phone validation by country/length or E.164 conversion (no country code is added)
  • Email deliverability checks (MX/DNS lookups, mailbox verification)
  • Deduplication or enrichment
  • Exposing the function as a Genie skill or MCP tool (later phase)
